Multi-Platform Publishing System

A build-light content system that turns familiar editorial tools into an accessible journal, photo gallery, interactive map, and message workflow.

Open live demoBack to projectsDiscuss this work

Problem

A nontechnical publisher needed to add journal entries, photographs, mapped stops, and reader messages without editing source code or operating a traditional CMS.

Solution

I built a static frontend around structured content rows and media references. Shared browser-side normalization turns those records into several connected experiences while keeping deployment simple.

Publishing workflow

  1. An editor adds or reviews structured content in familiar Google tools.
  2. Published rows provide a small, predictable data contract.
  3. The static site validates and normalizes records in the browser.
  4. One source powers home previews, journal cards, photo groups, and map stops.

Tech stack

System design

The frontend has no framework, database, application server, or required build step. Configuration defines content endpoints, map defaults, form integration, and ambient-media behavior. Reusable loaders handle CSV parsing, cache busting, visibility rules, safe fallbacks, media normalization, and loading states. Journal anchors, gallery clusters, and map markers share stable keys so visitors can move between views without losing context.

Experience details

  • Searchable journal and photo views
  • Grouped map markers and cross-page deep links
  • Lightbox and keyboard interactions
  • Video crossfades with reduced-motion fallback
  • Accessible validation and honest failure states

Technical judgment

The design favors the smallest system the content owner can operate confidently. Public data is treated as public, network failures degrade to local content, decorative video never carries essential information, and the form cannot pretend to submit when its destination is unavailable.

Portfolio adaptation

The public demo is not the client site. It uses the fictional Postcard Atlas identity, sanitized local fixtures, portfolio-scoped routes, and approved media while preserving the implementation’s visual and behavioral character.

Current boundary

Journal, photo, map, navigation, background-media, loading, and fallback behavior are available in the portfolio demo. Message delivery and live portfolio-owned Google content endpoints are intentionally disabled here; the demo uses sanitized local fixtures so those external integrations are not presented as live.

Outcome

The released portfolio case study demonstrates a low-maintenance publishing pattern that meets a content owner where they already work. Its public adaptation preserves the core architecture and interactions while deliberately substituting sanitized local fixtures for live Google endpoints and keeping message delivery disabled.
